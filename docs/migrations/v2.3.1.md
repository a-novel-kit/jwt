# Upgrading to v2.3.1

`v2.3.1` changes no code. It completes the Ed25519 rollout of the [v2.3.0 guide](v2.3.0.md), which
covered the token label but not the key label.

## Do I need to act?

| You use                                                          | Action                                               |
| ---------------------------------------------------------------- | ---------------------------------------------------- |
| Ed25519 keys generated on v2.3.x and read by verifiers on v2.2.x | **Required** — label the keys `EdDSA` during step 1. |
| Anything else                                                    | None.                                                |

## Label new keys `EdDSA` while a verifier runs v2.2.x

`jwk.GenerateED25519` labels keys `Ed25519` since v2.3.0. On v2.2.x, `jwk.ConsumeED25519` matches
only keys labeled `EdDSA`, so a v2.2.x verifier skips a key generated on v2.3.x. Every token that key
signs then fails to verify there, even one whose header still says `EdDSA`, because signing with
`jws.NewEdDSASigner` relabels the token and leaves the key as generated.

Step 1 of the rollout therefore relabels new keys as well as tokens:

```go
private, public, err := jwk.GenerateED25519()
if err != nil {
    return err
}

// Step 1: keep the key readable by verifiers on v2.2.x.
private.Alg, public.Alg = jwa.EdDSA, jwa.EdDSA
```

Drop the relabel in step 2, together with the switch to `jws.NewED25519Signer`. Keys already labeled
`Ed25519` remain usable by every v2.3.x verifier, so only the rollout window needs the legacy label.
