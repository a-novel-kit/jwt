# Upgrading to v2.5.0

`v2.5.0` brings two JSON Web Key behaviors in line with the JOSE specifications: the operations an
RSA-OAEP key declares, and the agreement between an EC private key and its public point.

## Do I need to act?

| You use                                      | Action                                 |
| -------------------------------------------- | -------------------------------------- |
| RSA-OAEP keys stored before v2.5.0           | **Required**: rewrite their `key_ops`. |
| EC JWKs whose `d` does not match `x` and `y` | **Required**: they no longer decode.   |
| RSA-OAEP keys generated by v2.5.0            | None.                                  |
| RSA or ECDSA signature keys                  | None. Their operations do not change.  |

## RSA-OAEP keys declare `wrapKey` and `unwrapKey`

RSA-OAEP is a key-management algorithm: the public key encrypts the content encryption key, and the
private key decrypts it. RFC 7517 §4.3 names those operations `wrapKey` and `unwrapKey`. The
`jwk.RSAOAEP` and `jwk.RSAOAEP256` presets gave the private half `encrypt` and the public half
`decrypt`, which reverses the roles and names content operations instead of key operations. They now
follow the AES key-wrapping presets, such as `jwk.A128KW`, which declare the same two operations.

| Half    | `key_ops` before | `key_ops` from v2.5.0 |
| ------- | ---------------- | --------------------- |
| Private | `["encrypt"]`    | `["unwrapKey"]`       |
| Public  | `["decrypt"]`    | `["wrapKey"]`         |

`jwk.ConsumeRSA` with either preset returns `jwk.ErrJWKMismatch` for a key that still carries the old
operations. Rewrite `key_ops` on every stored key as the table shows. The key material, `kid`, `use`
and `alg` stay the same. A JWKS that publishes the public half needs the same rewrite.

To verify, consume each rewritten key with the preset that generated it:

```go
privateKey, publicKey, err := jwk.ConsumeRSA(storedKey, jwk.RSAOAEP256)
```

## EC private keys must match their public point

`serializers.DecodeEC` built the private key from `d` alone and returned the `x` and `y` point as a
separate public key, without comparing the two. A JWK whose `d` belonged to another point decoded
without error, and its signatures never verified against the public key it published.

`DecodeEC` now returns `serializers.ErrInvalidECKey` for such a key, and `jwk.ConsumeECDSA` returns
the same error. Keys produced by `jwk.GenerateECDSA` or `serializers.EncodeEC` always match, so a key
that fails is corrupt. Regenerate it and publish the new public half.
