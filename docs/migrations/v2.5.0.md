# Upgrading to v2.5.0

`v2.5.0` brings two JSON Web Key behaviors in line with the JOSE specifications: the operations an
RSA-OAEP key declares, and the agreement between an EC private key and its public point. It also
enforces the rule that a header copy of the `iss`, `sub` or `aud` claim equals the payload's.

## Do I need to act?

| You use                                                  | Action                                    |
| -------------------------------------------------------- | ----------------------------------------- |
| RSA-OAEP keys stored before v2.5.0                       | **Required**: rewrite their `key_ops`.    |
| EC JWKs whose `d` does not match `x` and `y`             | **Required**: they no longer decode.      |
| A `HeaderProducerConfig` target that differs from claims | **Required**: issuing fails until agreed. |
| RSA-OAEP keys generated by v2.5.0                        | None.                                     |
| RSA or ECDSA signature keys                              | None. Their operations do not change.     |
| A `HeaderProducerConfig` without a target                | None. The header replicates no claim.     |

## RSA-OAEP keys declare `wrapKey` and `unwrapKey`

RSA-OAEP is a key-management algorithm: the public key encrypts the content encryption key, and the
private key decrypts it. RFC 7517 §4.3 names those operations `wrapKey` and `unwrapKey`. The
`jwk.RSAOAEP` and `jwk.RSAOAEP256` presets gave the private half `encrypt` and the public half
`decrypt`, which reverses the roles and names content operations instead of key operations. They now
follow the AES key-wrapping presets, such as `jwk.A128KW`, which declare the same two operations.

| Half    | `key_ops` before | `key_ops` from v2.5.0 |
| ------- | ---------------- | --------------------- |
| Private | `["encrypt"]`    | `["unwrapKey"]`       |
| Public  | `["decrypt"]`    | `["wrapKey"]`         |

`jwk.ConsumeRSA` with either preset returns `jwk.ErrJWKMismatch` for a key that still carries the old
operations. Rewrite `key_ops` on every stored key as the table shows. The key material, `kid`, `use`
and `alg` stay the same. A JWKS that publishes the public half needs the same rewrite.

To verify, consume each rewritten key with the preset that generated it:

```go
privateKey, publicKey, err := jwk.ConsumeRSA(storedKey, jwk.RSAOAEP256)
```

## EC private keys must match their public point

`serializers.DecodeEC` built the private key from `d` alone and returned the `x` and `y` point as a
separate public key, without comparing the two. A JWK whose `d` belonged to another point decoded
without error, and its signatures never verified against the public key it published.

`DecodeEC` now returns `serializers.ErrInvalidECKey` for such a key, and `jwk.ConsumeECDSA` returns
the same error. Keys produced by `jwk.GenerateECDSA` or `serializers.EncodeEC` always match, so a key
that fails is corrupt. Regenerate it and publish the new public half.

## Replicated header claims must match the payload

RFC 7519 §5.3 lets a token's header replicate its `iss`, `sub` and `aud` claims, so a recipient can
read them before decrypting a JWE. Each copy must equal the payload's claim. `jwt.HeaderProducerConfig`
sets these copies through its embedded `TargetConfig`, and nothing compared them with the claims the
token carried.

`Producer.Issue` now returns `jwt.ErrReplicatedClaimMismatch` when the header replicates a claim that
the payload holds with another value, or does not hold. `Recipient.Consume` returns the same error
for such a token, after its plugin verifies or decrypts it and before the claims are decoded. A claim
the header leaves out is not compared. An `aud` compares by value, so a bare `"api"` equals `["api"]`,
and several audiences must appear in the same order.

Build the header and the claims from one target:

```go
target := jwt.TargetConfig{Issuer: "accounts", Audience: jwa.Audience{"api"}, Subject: "user-123"}

producer := jwt.NewProducer(jwt.ProducerConfig{
    Header:  jwt.HeaderProducerConfig{TargetConfig: target},
    Plugins: plugins,
})

claims, err := jwt.NewBasicClaims(payload, jwt.ClaimsProducerConfig{TargetConfig: target})
```

When no recipient reads the header copies, leave `HeaderProducerConfig.TargetConfig` empty instead.
A service that maps token rejections to a status, such as 401, adds `jwt.ErrReplicatedClaimMismatch`
to that map.

A header that replicates a claim needs a payload that is a JSON claims set. The check therefore
rejects a nested JWT whose outer header replicates the inner token's claims. `DecodeUnverified` does
not compare the copies.
