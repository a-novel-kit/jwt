# Upgrading to v2.6.1

`v2.6.1` follows RFC 7515, 7516, 7518 and 7519 to the letter where earlier releases were lenient.
Tokens and keys that already met the specifications keep working unchanged.

## Do I need to act?

| You use                                                   | Action                                                  |
| --------------------------------------------------------- | ------------------------------------------------------- |
| Unsecured (`"alg":"none"`) tokens across several services | **Required**: upgrade every recipient before producers. |
| `PBES2KeyEncKWManagerConfig.SaltSize` between 1 and 7     | **Required**: issuing fails until the salt has 8 bytes. |
| RSA-OAEP keys shorter than 2048 bits                      | **Required**: replace the keys.                         |
| EC JWKs whose `x` or `y` drops leading zero octets        | **Required**: re-serialize them at full width.          |
| Signed or encrypted tokens, keys from this library        | None.                                                   |

## Unsecured tokens end with an empty signature segment

An unsecured JWS has three segments, the last one empty: `header.payload.` (RFC 7515 §7.1, RFC 7519
§6.1). Earlier releases issued `header.payload`. A producer now issues the RFC form, and
`jwt.DefaultRecipientPlugin` accepts both, so tokens issued before the upgrade keep decoding.

A recipient on v2.6.0 or earlier rejects the new form. Upgrade the recipients first, then the
producers.

The plugin also rejects a token whose header carries no `alg` at all, which earlier releases read as
`none`. RFC 7515 §4.1.1 makes `alg` required, and every `jwt.Recipient` now rejects such a token
before any plugin runs.

## Other tightened checks

- **Headers and claims are UTF-8** (RFC 7515 §5.2, RFC 7519 §7.2). A token holding an invalid UTF-8
  sequence fails with `jwt.ErrUnsupportedTokenFormat`. Earlier releases replaced the sequence.
- **`exp` is exclusive** (RFC 7519 §4.1.4). A token is expired from the instant `exp` plus the
  leeway, not one second later.
- **PBES2 salts hold 8 octets or more** (RFC 7518 §4.8.1.1), at issuance and at decryption.
- **RSA-OAEP keys hold 2048 bits or more** (RFC 7518 §4.3). Encrypting to or decrypting with a
  shorter key fails with `jwt.ErrInvalidSecretKey`.
- **Direct encryption carries no encrypted key** (RFC 7518 §4.5). A `dir` token with a non-empty
  second segment is rejected.
- **AES key wrap needs two blocks** (RFC 3394 §2): a content key shorter than 16 bytes no longer
  wraps. Every `enc` this library supports uses at least 16.
- **EC coordinates are full width** (RFC 7518 §6.2.1.2). `serializers.DecodeEC` rejects an `x` or
  `y` shorter than the curve's coordinate size with `serializers.ErrInvalidECKey`. Keys this library
  encoded since v2.0.1 already are.
- **An ECDH-ES ephemeral key is public** (RFC 7518 §4.6.1.1): an `epk` holding `d`, or a `kty` that
  does not match its curve, is rejected.
- **Private members match without regard to case.** `jwk.HasPrivateMaterial` and `jwk.Public`
  treat `D` like `d`, as the key decoders already did.

`jwt.DecodeToken` is deprecated. Call the decoder instead:

```go
token, err := (&jwt.SignedTokenDecoder{}).Decode(rawToken)
```
