# Upgrading to v2.3.0

`v2.3.0` brings the library in line with the current JOSE registries and RFCs: JWE key management
follows RFC 7516 and RFC 7518, Ed25519 signs under the RFC 9864 identifier, ML-DSA (RFC 9964) joins
the signature algorithms, and recipients stop accepting unsecured tokens by default. It also stops
`EmbedKey` publishing private key material.

The import path does not change and no exported function is removed. Several changes alter bytes on
the wire, so tokens produced by earlier versions may no longer decrypt or verify — read on.

## Do I need to act?

| You use                                              | Action                                                            |
| ---------------------------------------------------- | ----------------------------------------------------------------- |
| HMAC, RSA, or ECDSA JWS with matching presets        | **None.** Signing and verification are unchanged.                 |
| A recipient that consumes unsecured tokens           | **Required** — list `jwt.NewDefaultRecipientPlugin()` explicitly. |
| Ed25519 JWS across services                          | **Required** — see the staged rollout below.                      |
| ECDSA with a key off the preset's curve              | **Required** — it now errors instead of failing to verify.        |
| `jwp.EmbedKey` with `Embed: true`                    | **Required** — see below; it now errors rather than leaking.      |
| PBES2 (`jwek.PBES2*`)                                | **Required** if any ciphertext must outlive the upgrade.          |
| ECDH-ES (`jwek.ECDH*`) with `apu`/`apv` set          | **Required** if any token must outlive the upgrade.               |
| A hand-built `jwek.RSAOAEPKeyEncPreset`              | **Required** — `Hash` is now a `crypto.Hash`.                     |
| JWE key managers configured with `CEK`/`ProducerKey` | **Recommended** — drop the fields; they are ignored.              |
| ECDH-ES with `apu`/`apv` left empty                  | None. Encoded and decoded are the same value when both are empty. |
| Ed25519 private keys stored as JWKs                  | None. Both encodings of `d` load.                                 |
| A `jwk.Source` serving keys to sourced plugins       | None, unless its `key_ops` contradict the key's use.              |

## `EmbedKey` refuses a key that carries private material

`EmbedKey` writes the signing key into the token header so recipients can locate it — a verification
affordance, which needs the **public** half. Its `Source` resolves signing keys, private half
included, and nothing projected the key down. A producer wired as

```go
jwp.NewEmbedKey(jwp.EmbedKeyConfig{Source: signingKeySource, Embed: true})
```

emitted every token with the full private JWK inside it.

`Header` now returns `jwk.ErrPrivateKeyMaterial` instead. Pass the public half:

```go
public, err := jwk.Public(signingKey.JWK)
if err != nil {
    return err
}

jwp.NewEmbedKey(jwp.EmbedKeyConfig{Key: public, Embed: true})
```

A symmetric key cannot be embedded at all — it is its own secret, and `jwk.Public` refuses it. Use
`KID` or `URL` to point recipients at the key instead.

**If your tokens were carrying a private key, treat it as disclosed.** Rotate the signing key; every
holder of a token has it.

## PBES2 derives the wrap key from the specified salt

RFC 7518 §4.8.1.1 requires the PBKDF2 salt to be `UTF8(Alg) || 0x00 || Salt Input`, where _Salt
Input_ is the base64url-**decoded** `p2s`. Earlier versions passed the still-encoded `p2s` text and
omitted the algorithm prefix.

Encryption and decryption used the same wrong value, so the round trip was self-consistent — but no
compliant implementation derived the same wrap key, and none of ours interoperated with anyone
else's.

**Existing ciphertext does not decrypt under v2.3.0.** There is no in-place migration: the wrap key
is different, so the content key cannot be recovered. Decrypt with v2.2.x and re-encrypt with
v2.3.0, or accept the loss where the data is transient.

`Iterations` and `SaltSize` now apply defaults when left non-positive
(`DefaultPBES2Iterations`, `DefaultPBES2SaltSize`). A zero `SaltSize` previously produced a
zero-length salt with no error, so every token derived from one password shared a wrap key; a zero
`Iterations` produced `p2c=0`, which the decoder rejects, so the token was undecryptable and only
the recipient found out.

## ECDH-ES agreement parameters are base64url-encoded

RFC 7518 §4.6.1.2 and §4.6.1.3 define `apu` and `apv` as base64url-encoded values. Earlier versions
wrote `ProducerInfo` and `RecipientInfo` into the header raw, and fed the header field to the KDF
without decoding it — the opposite of what the KDF expects.

Both are now handled correctly: the header carries the encoded form, and the derivation mixes in the
decoded bytes.

`ProducerInfo` and `RecipientInfo` are unchanged — still plain strings you supply, now encoded for
you. Nothing to change in your configuration.

**Tokens issued with a non-empty `apu` or `apv` do not decrypt under v2.3.0**, for the same reason as
PBES2. Tokens that left both empty are unaffected, since the encoded and decoded forms of an empty
value are identical — which is also why no round-trip test ever caught this.

## ECDSA keys are checked against the preset's curve

RFC 7518 §3.4 binds each algorithm to one curve: ES256 to P-256, ES384 to P-384, ES512 to P-521. The
binding lives in the key payload's `crv`, which the header-level preset match cannot see — it
compares `kty`, `use`, `key_ops` and `alg` only.

So `jwk.ConsumeECDSA` accepted a key labelled `ES256` that carried a P-384 point, and
`jws.ECDSAVerifier` verified with whatever key it was given. An operator who configured ES256 did not
enforce ES256, and nothing said so: a mismatched key simply failed to verify, which reads as a bad
token rather than a misconfigured verifier.

`ConsumeECDSA` now returns `ErrJWKMismatch` naming both curves, and `ECDSAVerifier` returns
`jwt.ErrInvalidSecretKey` when its key is off the preset's curve.

Keys generated by `jwk.GenerateECDSA` with the matching preset are unaffected — the curve is the one
the preset asked for. If a source has been serving keys under the wrong `alg` label, the label is
wrong and those tokens were never verifiable by a conforming implementation; correct the label at the
source.

## Recipients reject unsecured tokens unless configured for them

RFC 7518 §3.6 forbids accepting unsecured (`"alg":"none"`) tokens by default. A `jwt.Recipient` built
without plugins consumed them anyway, so a configuration that lost its plugins accepted forged tokens.
A recipient without plugins now rejects every token with `jwt.ErrMismatchRecipientPlugin`.

To keep consuming unsecured tokens, say so:

```go
// before
jwt.NewRecipient(jwt.RecipientConfig{})

// after
jwt.NewRecipient(jwt.RecipientConfig{
    Plugins: []jwt.RecipientPlugin{jwt.NewDefaultRecipientPlugin()},
})
```

`DecodeUnverified` runs no plugin and is unaffected. Two further checks from the JWT BCP update
(draft-ietf-oauth-rfc8725bis) apply to every recipient: a token holding any character outside the
base64url alphabet and `.` is rejected with `jwt.ErrUnsupportedTokenFormat`, and the new
`RecipientConfig.Typ` rejects a token whose `typ` header declares another media type.

## Ed25519 signs under the `Ed25519` algorithm

RFC 9864 deprecates the polymorphic `EdDSA` identifier for the fully-specified `Ed25519`. Signers now
write `"alg":"Ed25519"`, and `jwk.GenerateED25519` labels new keys `Ed25519`. Verifiers and
`jwk.ConsumeED25519` accept both labels, so tokens and keys issued before the upgrade keep working.

A verifier still on v2.2.x rejects the new identifier, so roll out in two steps:

1. Upgrade every service. Where a service signs tokens that a peer verifies, sign with
   `jws.NewEdDSASigner` or `jws.NewSourcedEdDSASigner` in this step, so the peer keeps accepting
   them whichever upgrades first.
2. Once every verifier runs v2.3.0, switch those signers to `jws.NewED25519Signer` and
   `jws.NewSourcedED25519Signer`.

```go
// step 1
jws.NewEdDSASigner(privateKey)

// step 2
jws.NewED25519Signer(privateKey)
```

A deployment whose verifiers all upgrade before any signer can skip step 1. `jwa.EdDSA` and the
`EdDSA` constructors are deprecated; replace `jwa.EdDSA` with `jwa.Ed25519` wherever you configure an
algorithm.

Private keys now serialize `d` as the 32-byte private key RFC 8037 specifies, which other JOSE
libraries read. Earlier versions wrote the 64-byte seed-and-public-key form; it still loads.

## JWE key managers draw a fresh key for every token

RFC 7516 §5.1 requires a new content encryption key for each token, and ECDH-ES (RFC 7518 §4.6) a new
ephemeral key. The managers took both from their configuration, so every token a `Producer` issued
shared one content key and one "ephemeral" key. They now generate both per token. The `CEK` fields of
the AES-KW, AES-GCMKW, RSA-OAEP, PBES2, and ECDH-ES+KW configs, and the `ProducerKey` fields of the
ECDH-ES configs, are deprecated and ignored. Remove them:

```go
// before
jwek.NewAESKWManager(&jwek.AESKWManagerConfig{CEK: cek, WrapKey: wrapKey}, jwek.A256KW)

// after
jwek.NewAESKWManager(&jwek.AESKWManagerConfig{WrapKey: wrapKey}, jwek.A256KW)
```

Recipients need no change. The same fix makes `A128GCMKW`, `A192GCMKW`, and `A256GCMKW` work: their
`iv` and `tag` never reached the serialized header, so no recipient could decrypt those tokens. The
ECDH-ES `epk` header also gains the `"kty":"OKP"` member RFC 7518 requires, so other implementations
accept it.

A decryptor now refuses a token carrying a `zip` header with `jwt.ErrUnsupportedTokenFormat`. The
library does not decompress, and returned the compressed bytes as the payload.

## Sourced plugins honor `key_ops`

A sourced signer now uses only keys whose `key_ops` include `sign`, and a sourced verifier only keys
whose `key_ops` include `verify`. A private key labeled for verification was previously used to
sign. Keys generated by this package carry the right operations; a source serving hand-labeled keys
should check that their `key_ops` match their use.

## RSA-OAEP presets name their hash

`jwek.RSAOAEPKeyEncPreset.Hash` held a `hash.Hash` instance, and every manager and decoder built from
one preset wrote to it. Concurrent encryptions corrupted each other's digest. The field is now a
`crypto.Hash`, which carries no state. The `RSAOAEP` and `RSAOAEP256` presets need no change; a
hand-built preset does:

```go
// before
jwek.RSAOAEPKeyEncPreset{Alg: jwa.RSAOAEP256, Hash: sha256.New()}

// after
jwek.RSAOAEPKeyEncPreset{Alg: jwa.RSAOAEP256, Hash: crypto.SHA256}
```

## Notes

ML-DSA (RFC 9964) is new and needs no migration: `jwk.GenerateMLDSA`, `jwk.ConsumeMLDSA`, and the
`jws.MLDSA*` signers and verifiers, at the ML-DSA-44, ML-DSA-65, and ML-DSA-87 levels. Its keys use
the `AKP` key type, whose private `priv` member `jwk.Public` strips like any other private member.
